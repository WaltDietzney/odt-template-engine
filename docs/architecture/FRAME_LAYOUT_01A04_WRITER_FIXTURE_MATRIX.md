# FRAME-LAYOUT-01A.4 — Writer Fixture Matrix

## 1. Purpose

This document records LibreOffice Writer-authored evidence for FRAME-LAYOUT-01.

The fixture was created interactively in Writer rather than generated by the engine. Its purpose is to establish how Writer represents ordinary frame/image/text-box placement choices before any public Frame Layout API or production correction is designed.

This is evidence, not an API contract.

## 2. Fixture 1 — baseline positioning evidence

Source fixture:

```text
FRAME-LAYOUT-01A.odt
```

The first fixture contains representative image and text-box objects created through Writer UI operations.

### 2.1 Paragraph-relative horizontal alignment

Writer-authored image cases establish the native graphic-property model:

```text
left:
    style:horizontal-pos="left"
    style:horizontal-rel="paragraph"

center:
    style:horizontal-pos="center"
    style:horizontal-rel="paragraph"

right:
    style:horizontal-pos="right"
    style:horizontal-rel="paragraph"
```

The equivalent text-box cases use the same semantic dimensions.

This confirms that horizontal alignment and horizontal reference area are independent native properties and belong to `style:graphic-properties`.

### 2.2 Paragraph-relative vertical alignment

Writer-authored text-box cases establish:

```text
top:
    style:vertical-pos="top"
    style:vertical-rel="paragraph"

middle:
    style:vertical-pos="middle"
    style:vertical-rel="paragraph"

bottom:
    style:vertical-pos="bottom"
    style:vertical-rel="paragraph"
```

This independently confirms the A0.2 conclusion that position values are orientation/alignment enums, not percentage coordinates.

### 2.3 Anchor types observed

The fixture also contains Writer-authored examples using:

```text
text:anchor-type="char"
text:anchor-type="as-char"
```

The `as-char` example demonstrates a baseline-related vertical model, including:

```text
style:vertical-pos="top"
style:vertical-rel="baseline"
```

The exact relation used by Writer varies with the selected anchor/layout option. This is evidence that anchor type, position and relation are semantically related dimensions and must not be treated as arbitrary independent strings.

### 2.4 Structural ownership confirmed

The Writer fixture reinforces the native ownership split established in A0.2:

```text
draw:frame
    -> text:anchor-type
    -> svg:width / svg:height
    -> coordinates where applicable

style:graphic-properties
    -> style:horizontal-pos
    -> style:horizontal-rel
    -> style:vertical-pos
    -> style:vertical-rel
    -> wrap/layout policy
```

The current historical DrawTextBox path therefore cannot be considered authoritative merely because it can serialize similarly named values directly on a frame.

## 3. Fixture-authoring lesson

The Writer UI does not expose ODF vocabulary such as `svg:x` and `svg:y` directly.

Future Writer fixture instructions should therefore describe **user-visible Writer operations**, not XML attributes.

For example, instead of asking the fixture author to create:

```text
from-left + svg:x
```

the research procedure should ask for an object positioned by an explicit horizontal distance in Writer and then inspect which ODF combination Writer serializes.

The same rule applies to vertical offsets.

This keeps Writer as the source of native serialization evidence rather than asking the fixture author to reverse-engineer ODF concepts through the UI.

## 4. Fixture 2 — exploratory layout evidence

A second Writer-authored fixture was created by varying additional layout options without requiring the combinations to produce aesthetically useful layout:

```text
FRAME-LAYOUT-01A-2.odt
```

Its visual appearance is intentionally not normative. It is a research fixture for discovering Writer serialization.

Observed Writer-generated graphic properties include representative values from these dimensions:

```text
style:wrap:
    none
    dynamic
    parallel
    left
    right
    run-through

style:run-through:
    foreground

style:horizontal-pos:
    left
    center
    right

style:horizontal-rel:
    paragraph
    paragraph-content

style:vertical-pos:
    top
    middle
    bottom
    from-top

style:vertical-rel:
    paragraph
    paragraph-content
    baseline

draw:wrap-influence-on-position:
    once-concurrent

loext:allow-overlap:
    true
    false
```

Writer also emits contour-related properties in some combinations:

```text
style:wrap-contour
style:wrap-contour-mode
style:number-wrapped-paragraphs
```

### 4.1 Important new evidence: from-top

The exploratory fixture contains a Writer-generated style using:

```text
style:vertical-pos="from-top"
style:vertical-rel="paragraph"
```

This is important because the fixture author did not need to manipulate ODF manually. Writer itself selected the native `from-top` mode as a consequence of an ordinary UI operation.

The associated frame must be inspected together with its graphic style to determine the concrete coordinate carrier used by Writer. The style alone is not sufficient to characterize the complete coordinate model.

### 4.2 Wrap is richer than one boolean

The fixture confirms that Writer's wrap model is not reducible to a single `wrap=true/false` flag.

At minimum, FRAME-LAYOUT research must distinguish the native modes evidenced above. Contour behavior and wrap influence are related but separate dimensions.

No final 1.0 public vocabulary is decided here.

### 4.3 Overlap is a LibreOffice extension in this fixture

Writer serializes the tested overlap choice as:

```text
loext:allow-overlap="true|false"
```

This must be treated separately from standard ODF properties during API/design work. FRAME-LAYOUT must explicitly decide whether a LibreOffice extension belongs in the bounded 1.0 API, a compatibility/raw path, or future work.

### 4.4 Writer uses different reference areas

The fixture demonstrates both:

```text
paragraph
paragraph-content
```

as relation values.

A future friendly API must therefore not collapse alignment and reference area into one concept.

## 5. Consolidated A0.4 findings

The Writer fixtures now provide direct evidence for these semantic dimensions:

1. anchor type;
2. horizontal orientation/alignment;
3. horizontal reference area;
4. vertical orientation/alignment;
5. vertical reference area;
6. coordinate-oriented modes such as `from-top`;
7. wrap mode;
8. contour-related wrap behavior;
9. wrap influence on position;
10. overlap policy;
11. object-local size/geometry.

This strongly supports the A0.2 candidate semantic decomposition.

If the fixture contains an equivalent horizontal free-position case, characterize it in the same way.

## 7. Status

**A0.4 baseline positioning evidence: confirmed.**

The first Writer fixture is sufficient to freeze paragraph-relative left/center/right, top/middle/bottom, and char/as-char evidence.

The second exploratory fixture already contains useful additional evidence for wrap, relation areas, overlap, and coordinate-oriented positioning. It should be mined rather than recreated.

## 8. Fixture 2 XML evidence pass

The exploratory fixture was inspected at the concrete `draw:frame` + referenced graphic-style level.

### 8.1 Confirmed Writer coordinate-mode pair

Writer produced a paragraph-anchored frame with:

```xml
<draw:frame
    text:anchor-type="paragraph"
    svg:y="0.302cm"
    .../>
```

whose graphic style contains:

```xml
<style:graphic-properties
    style:vertical-pos="from-top"
    style:vertical-rel="paragraph"
    .../>
```

This is the concrete Writer-authored pair FRAME-LAYOUT-01 needed:

```text
vertical orientation mode = from-top
vertical reference area   = paragraph
vertical coordinate       = svg:y = 0.302cm
```

It matches the ODF rule established in A0.2: when `style:vertical-pos="from-top"`, the associated `svg:y` value carries the concrete offset.

### 8.2 Writer may serialize coordinates even when the alignment mode does not use them

Other Writer-authored text frames in the same fixture contain `svg:y` values while their graphic styles use semantic alignment modes:

```text
middle + paragraph
    svg:y = -3.032cm

bottom + paragraph
    svg:y = 0.699cm
```

ODF defines `svg:y` as layout-significant for text-document frame positioning when the vertical mode is `from-top`; otherwise Writer/ODF alignment semantics are governed by the position enum.

Therefore FRAME-LAYOUT must not infer "absolute vertical positioning" merely from the presence of `svg:y`.

The semantic mode controls whether the coordinate is operative.

The same principle applies horizontally: `svg:x` is only layout-significant for the coordinate-oriented horizontal modes such as `from-left` / `from-inside`.

### 8.3 No Writer-authored horizontal from-left case was captured

Fixture 2 contains no graphic style with:

```text
style:horizontal-pos="from-left"
```

Therefore the horizontal coordinate path remains supported by ODF/Writer source evidence, but this fixture does not add a Writer-authored concrete `from-left + svg:x` example.

This is not a blocker for A0 synthesis. A dedicated horizontal free-position fixture can be added later if API design requires exact Writer round-trip evidence.

### 8.4 Wrap matrix confirmed at concrete frame/style level

Fixture 2 contains Writer-generated graphic styles using:

```text
style:wrap="none"
style:wrap="dynamic"
style:wrap="parallel"
style:wrap="left"
style:wrap="right"
style:wrap="run-through"
```

Some combinations additionally emit:

```text
style:run-through="foreground"
style:wrap-contour="true|false"
style:wrap-contour-mode="full|outside"
style:number-wrapped-paragraphs="no-limit"
```

This confirms that wrap mode, run-through behavior, contour wrapping, and paragraph-count behavior are distinct native dimensions.

FRAME-LAYOUT-01 should not flatten them into one generic wrap flag.

### 8.5 Wrap influence and overlap confirmed

Several Writer-authored image styles contain:

```text
draw:wrap-influence-on-position="once-concurrent"
loext:allow-overlap="true|false"
```

This confirms:

- wrap influence is independent of `style:wrap`;
- overlap is serialized separately;
- `loext:allow-overlap` is a LibreOffice extension and should remain explicitly identified as such.

### 8.6 Relation areas confirmed

Writer uses both:

```text
paragraph
paragraph-content
```

in the same fixture.

For example, outer Writer frames use paragraph-relative positioning, while image frames commonly use paragraph-content-relative positioning.

This further confirms that "align left/center/right" is incomplete semantics without the corresponding reference area.

### 8.7 Anchor-specific evidence

The fixture contains:

```text
text:anchor-type="char"
text:anchor-type="as-char"
```

The `as-char` image uses:

```text
style:vertical-pos="top"
style:vertical-rel="baseline"
```

while the char-anchored case uses paragraph-content relations.

Together with A0.3, this reinforces that anchor type affects both valid relation semantics and insertion/container semantics.

### 8.8 flow-with-text status

The fixture does contain:

```text
style:flow-with-text="false"
```

but only in Writer's common/default graphic-style configuration, not as a clearly isolated object-level experimental toggle tied to one of the fixture objects.

Therefore Fixture 2 does **not** yet establish a useful round-trip characterization of per-object `flow-with-text` behavior.

This property remains supported by ODF/Writer source evidence and by current engine characterization, but a dedicated Writer UI fixture would be needed if FRAME-LAYOUT-01 intends to expose it as a first-class 1.0 friendly option.

## 9. A0.4 conclusion

The Writer evidence is now sufficient to confirm the central placement model:

```text
anchor
+
orientation mode
+
reference area
+
optional coordinate active only in coordinate-oriented modes
+
wrap policy
+
related layout policy
```

Most importantly, Writer itself demonstrated the concrete vertical coordinate form:

```text
style:vertical-pos="from-top"
style:vertical-rel="paragraph"
svg:y="0.302cm"
```

The fixture also shows why the engine must not treat the mere presence of `svg:x/y` as proof that a frame is using absolute/free positioning: Writer can retain coordinate values on objects whose active mode is `middle`, `bottom`, or another semantic alignment.

A0.4 is therefore complete enough for architecture synthesis.

Remaining evidence gaps such as a Writer-authored horizontal `from-left + svg:x` example or a dedicated per-object `flow-with-text` toggle should only be pursued if the synthesis identifies them as required for the bounded 1.0 API.
