# H03 – Native editable geometry: architecture and change contract (draft)

Status: **Approved for H03 implementation on 23 November 2026; merge requires separate approval.**
Baseline: `forgejo/develop` at `22fe57b` (H02 merge). Branch: `feature/h03-native-geometry`.
Source: CV Generator Pro `research/E009-ARCHITEKTUR-UND-ENGINE-HANDOFF-2026-11-17.md` and E009 Writer PoC; engine `DrawingLayout`, `DrawingLayoutProjector`, `CircularImageElement`, `StyleRequirement`, `FillImageRequirement`.

## Goal and first vertical slice

Author **native, Writer-editable ODF geometry**, not rasterized drawings or arbitrary XML snippets. The first engine-generated proof comprises (1) a solid-filled rectangle, (2) a bitmap-filled ellipse, and (3) an arrow-like editable contour, using existing structured insertion, layout, style and resource facilities. Writer PoC evidence demonstrates feasibility, **not** engine support.

## Responsibilities

- `ShapeElement` (proposed): one public structured element, composing geometry, appearance, `DrawingLayout`, optional transformation and dependencies; no CV-specific behavior.
- `ShapeGeometry` (proposed): validated presets and constrained contour definitions in a local viewBox independent of physical dimensions. Internal carrier selection (`draw:custom-shape` or other native carrier) follows verified ODF semantics; no public class per shape.
- `ShapeAppearance` (proposed): none/solid/bitmap fill, stroke and fill transparency; distinguish fill transparency from object transparency. Emit deterministic `StyleRequirement` identities.
- **Reuse** `DrawingLayout` and `DrawingLayoutProjector` for anchors, sizes, offsets/alignment and wrap. Do not duplicate mutable layout state. Endpoints for line carriers require separate research because layout width/height currently reject nonpositive dimensions.
- **Reuse** `FillImageRequirement`, resource collection, package/manifest materialization and structured insertion. Missing bitmap files and conflicting resource identities must fail explicitly.
- `ShapeTransform` (proposed, deferred until rotation evidence): rotation origin/order must be specified before an API is committed. Z-order is independent of rotation.

## Compatibility and scope boundaries

Existing `ImageElement`, `CircularImageElement`, frame APIs, public/protected extension points and repeated render/save behavior must remain compatible. No changes to CV data contracts or visual-template schema. Text in shapes, grouping, general enhanced-geometry formula language, full arrow composition and unrelated E006/E010/E011/E012 work are **out of scope** for the first slice. Do not generalize unsupported anchor/transform combinations by fallback.

## Implementation slices and evidence gates

1. Characterize existing insertion, `CircularImageElement` custom-shape output, style and fill-image pipelines; record the exact ODF carriers from E009 evidence and the three proof cases. Resolve whether a bitmap-backed shape can share the current image resource packaging without an ImageElement inheritance dependency.
2. Implement minimal geometry/appearance/element with strict validation; demonstrate all three shapes in generated ODT with no post-hoc XML patching. Keep first-slice carrier and anchor combinations narrow and explicit.
3. Unit tests for geometry/appearance validation and layout projection; integration tests for content.xml, styles.xml, manifest, insertion and repeated rendering, plus image/shape resource collisions.
4. LibreOffice open/edit/save/reopen and PDF/visual regression for the three proof cases; preserve artifacts and document unsupported variants. Run focused tests, PublicSampleSmokeTest, full `composer test`, PHP lint and `git diff --check` as applicable.

## Open architecture decisions before implementation

- Which exact native carriers and enhanced paths from E009 are stable for the rectangle, ellipse and contour?
- How will `ShapeElement` expose bitmap resource dependencies through the existing collector without coupling to `ImageElement`?
- Which initial anchor/layout combinations and transparency semantics are actually supported by Writer roundtrip?
- Are rotation and generic line endpoints postponed to a later H03 slice? **Proposed: yes**, unless needed for one of the three proofs.

Acceptance: all three editable shapes generated by the engine, deterministic style/resource integration, compatibility regression green, Writer human gate recorded. No merge without separate approval.

## Phase A evidence check (23 November 2026)

- E009 ODF evidence records native `draw:custom-shape` with `draw:enhanced-geometry`: rectangle (`M ... L ... Z N`), ellipse (`U ... Z N`) and further contours. A bitmap graphic style references `draw:fill-image-name=E009Bitmap` and a `draw:fill-image` declaration. This confirms carrier examples, not all engine integration cases.
- `CircularImageElement::toDomNode()` already emits `draw:custom-shape` and ellipse enhanced geometry. Its legacy behavior is characterization material, **not** a base class for generic shapes.
- `OdtElement` already exposes `getOwnStyleRequirements()`, `getOwnFillImageDependencies()` and `getOwnImageAssets()`; `StructuredResourceCollector` walks the latter. Therefore a bitmap shape can supply physical assets through the existing element hook without inheriting `ImageElement`. Verify packaging conventions and filename collisions in implementation tests.
- `DrawingLayout` explicitly validates anchors, dimensions and alignment; `DrawingLayoutProjector` separates object attributes from graphic layout properties. Phase one should start with the paragraph anchor demonstrated by E009, not promise all anchors without roundtrip evidence.

**Architecture recommendation:** keep H03 first-slice API limited to named preset/validated path geometry, fill/stroke appearance and existing DrawingLayout. Treat rotation, line endpoints and arbitrary enhanced geometry expressions as later evidence-driven extensions. No further Writer feasibility PoC is required for the already documented E009 examples; engine-generated roundtrip and compatibility tests remain mandatory.
